# 메모리 검사와 부하 측정

```sh
sudo apt-get install valgrind apache2-utils
make valgrind
make sanitize-test
make bench
```

- `make valgrind`는 Linux에서 프록시와 백엔드 둘 다 Valgrind로 실행한다. 실제 TCP 연결로 정적 GET, 프록시 GET과 POST를 확인하고, 두 서버를 SIGINT로 순서대로 종료한다. 프로세스 종료 코드, 남은 힙, 메모리 오류, 상속된 표준 입출력 외에 남은 FD를 검사한다. 원본 로그는 `build/valgrind/{proxy,backend}.log`에 저장된다.
- `make sanitize-test`는 ASan·UBSan 설정으로 단위 테스트와 전체 HTTP 통합 테스트를 실행한다.
- `make bench`는 `127.0.0.1`에 임시 프록시와 백엔드를 실행한다. 1 KiB 응답을 프록시에서 직접 서빙하거나 백엔드에서 읽어 중계한다. 요청 수는 케이스마다 1,000개로 고정한다. 프록시 작업자 8·64개, 정적·프록시 경로, 동시 접속 1·10·50·100개, 클라이언트 keep-alive 끔·켬을 조합해 32개 케이스를 실행한다. 백엔드 작업자 8개와 연결 큐 256개는 동일하다.
- 기본 출력인 `build/bench.csv`에는 환경과 완료 요청 수, keep-alive 응답 수, 처리량(req/s), 평균·p95 요청 지연(ms), failed, non-2xx가 담긴다. 재현할 때 `BENCH_REQUESTS`와 `BENCH_REPORT`로 요청 수와 파일 경로를 지정할 수 있다.

## WSL2 측정 결과

측정 시작 2026-11-25T02:13:32+00:00. WSL2 Ubuntu, 커널 `6.18.33.2-microsoft-standard-WSL2`, AMD Ryzen 5 7535HS, 논리 CPU 12개.
각 케이스에서 ApacheBench의 완료 값은 1,000, non-2xx는 0으로 기록됐다.
아래 표의 각 셀은 작업자 **8개 / 64개** 순서다. failed는 ApacheBench가 실패로 분류한 요청 수다.

- 동시 50개의 keep-alive에서 작업자를 8개에서 64개로 늘리면 정적 처리량은 49.72에서 1,139.55 req/s, 프록시 처리량은 65.99에서 10,488.45 req/s로 올랐다. 두 경로의 failed도 각각 24건에서 0건으로 줄었다.
- 동시 100개에서는 작업자 64개에서도 keep-alive 실패가 남았다. 프록시 처리량은 33.10에서 196.78 req/s로 올랐지만 failed도 48건에서 55건으로 늘었다. 처리량과 함께 failed 및 p95를 봐야 하는 이유다.
- 이 서버에서 작업자 스레드는 다음 요청을 기다리는 동안에도 keep-alive 연결 하나를 계속 맡는다. 작업자를 늘리면 동시에 맡을 수 있는 연결이 많아지고, 스레드 스택과 스케줄링 비용도 늘 수 있다. 이 결과는 작은 응답을 로컬에서 순서대로 한 차례 측정한 기록이다.
- 정적 경로는 헤더와 파일 조각을 나눠 전송한다. 프록시 경로는 백엔드 응답을 받은 뒤 이 크기의 응답이라면 헤더와 본문을 함께 전송한다. 두 경로의 처리량에는 이 전송 방식 차이도 포함된다.
