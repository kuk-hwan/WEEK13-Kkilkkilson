# 포워드 프록시와 CONNECT 터널을 넣는다

처음 명세와 참고 구현은 Reverse Proxy만 만들고 Forward Proxy·CONNECT 터널은 범위 밖에 뒀다. 같은 실행 파일에 포워드 프록시를 더한다. 프록시 동작을 두 방향 다 보여 주려는 것이고, CONNECT가 없으면 HTTPS 사이트에 쓸 수 없어 함께 넣는다.

- **요청 대상의 형식으로 나눈다.** absolute-form과 CONNECT는 포워드 프록시로, origin-form은 지금 순서(라우트 → 동적 엔드포인트 → 정적 파일)로 간다. 포워드 요청에는 라우트를 적용하지 않는다. 그래서 두 프록시를 같이 켜도 우선순위가 겹치지 않는다.
- **허용 목록이 켜는 스위치다.** `--forward-allow CIDR`이 하나라도 있어야 켜지고, 목록 밖 클라이언트는 403을 받는다. 켜 놓고 막는 걸 잊는 열린 프록시를 만들 수 없다. 루프백만 허용하는 규칙을 코드에 박아 두는 방법도 있었지만, 그러면 거절하는 경우를 테스트로 확인할 수 없어서 고르지 않았다. 목적지는 제한하지 않는다.
- **목적지 주소는 요청마다 `getaddrinfo`로 찾는다(IPv4, 첫 주소).** 블로킹이라 DNS 시간은 3초 백엔드 deadline에 들어가지 않는다. 별도 스레드나 비동기 DNS는 이 과제 크기에 비해 크다.
- **터널은 작업자 하나를 끝날 때까지 쓴다.** 연결 하나를 작업자 하나가 맡는 구조를 그대로 둔다. 양쪽 5초 유휴면 닫아 상한을 두지만, 브라우저가 터널을 여러 개 열면 작업자가 모자라 503이 날 수 있다. 동시 터널 수 제한은 두지 않고 README에 `--workers`를 늘리라고 적는다.

## Consequences

- 요청 파서가 absolute-form과 authority-form, CONNECT를 받게 되어 파서의 반환 규칙이 바뀐다. 포워드 프록시가 꺼져 있을 때는 app이 지금처럼 400·501로 거른다.
- 응답 처리(8 MiB 한도, 3초 deadline, 502·504, 재시도 없음)는 리버스 프록시와 같다. 인터넷의 큰 페이지나 느린 사이트는 실패할 수 있다.
