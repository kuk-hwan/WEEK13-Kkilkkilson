# 미니 웹서버 명세

13주차 과제 "C 언어로 동작하는 웹서버"의 명세다. 티켓(`/to-tickets`)은 이 문서가 머지된 뒤에 만든다.

## 문제

외부 HTTP·이벤트 루프 라이브러리 없이 POSIX 소켓 API만으로 웹서버를 처음부터 짜야 한다. 정적 파일 서빙에서 끝나지 않고 동적 요청 처리, 동시 요청 처리, 프록시까지 들어가야 한다. 프록시는 Reverse Proxy로 시작했고, 나중에 Forward Proxy(CONNECT 터널 포함)를 더했다([ADR-0001](adr/0001-forward-proxy.md)).

세 명이 나눠 만들려면 무엇을 어디까지 만들지, 모듈 경계와 한도가 먼저 정해져 있어야 한다. 포트폴리오에 넣을 수준이라 정상 요청뿐 아니라 잘못된 요청, 갑작스러운 끊김, 백엔드 장애에서도 정해진 대로 동작해야 하고, 그걸 테스트와 측정 기록으로 보여 줄 수 있어야 한다.

## 해결

실행 파일 하나(`mini-webserver`)를 만든다. 같은 실행 파일이 앞단 Reverse Proxy도 되고 뒤의 백엔드도 되고, 허용 목록을 주면 Forward Proxy도 된다. 실행할 때 CLI 인자로 포트, 정적 파일 루트, 라우트, 허용 목록을 받는다.

요청 하나는 이렇게 흐른다: `accept` → 연결 큐 → 작업자 스레드 → 요청 파싱 → 분기(포워드 요청이면 목적지 서버로 전달 또는 터널 / 라우트에 걸리면 백엔드로 전달 / 동적 엔드포인트 / 정적 파일) → 응답. HTTP/1.1 keep-alive면 같은 작업자가 같은 연결에서 다음 요청을 읽는다.

### 정한 것

| | 결정 | 쉬운 뜻 |
|---|---|---|
| ① 개발·빌드 환경 | WSL2 Ubuntu + Makefile. macOS에서도 같은 소스로 빌드된다 | 어디에서 만들고 어떻게 실행할지 |
| ② 동시 처리 방식 | pthread 스레드 풀 + 크기 제한 연결 큐 | 여러 연결을 미리 만든 작업자에게 나눠 맡기기 |
| ③ 프록시 종류 | Reverse Proxy + Forward Proxy(CONNECT 터널 포함) | 서비스 앞에서 요청을 받고 백엔드에 전달하기 + 클라이언트가 고른 목적지 서버로 대신 가 주기 |
| ④ 라우팅 기준 | 경로 접두사 기반, 가장 긴 접두사 우선 | `/api/`처럼 요청 주소를 보고 전달할 곳 결정 |
| ⑤ 백엔드 선택 방식 | 라우트마다 라운드 로빈 | A → B → A 순서로 배분하기 |
| ⑥ 정적·동적 처리 | 정적 파일은 직접 응답, 동적 요청은 C 로직 또는 백엔드 전달 | 파일과 기능 요청을 어떻게 처리할지 |
| ⑦ HTTP 지원 범위 | GET·HEAD·POST, HTTP/1.0·1.1, Content-Length 기반 본문, keep-alive | 어떤 요청을 어디까지 처리할지 |
| ⑧ 실행 설정 방식 | CLI 인자 | 포트·파일 루트·백엔드 전달 규칙·허용 목록을 실행할 때 지정 |

HEAD는 과제 최소 범위(GET·POST)에 없지만 `curl -I`로 확인할 수 있게 넣는다. GET과 같고 본문만 보내지 않는다.

## 사용자 이야기

### 브라우저·curl 사용자

1. 사용자로서, 서버 주소(`/`)를 열면 루트의 `index.html`을 받고 싶다. 그래야 데모 페이지를 바로 볼 수 있다.
2. 사용자로서, HTML·CSS·JS·PNG·JPG·SVG 같은 파일을 맞는 `Content-Type`으로 받고 싶다. 그래야 브라우저가 제대로 그린다.
3. 사용자로서, 없는 파일을 요청하면 404와 짧은 오류 페이지를 받고 싶다. 그래야 주소를 잘못 쳤다는 걸 안다.
4. 사용자로서, 읽을 권한이 없는 파일을 요청하면 403을 받고 싶다. 그래야 서버 고장과 구분한다.
5. 사용자로서, 디렉터리를 요청하면 그 안의 `index.html`을 받고 싶다. 그래야 `/docs/`처럼 끝이 `/`인 주소가 동작한다.
6. 사용자로서, `index.html`이 없는 디렉터리를 요청하면 403을 받고 싶다. 파일 목록은 보이지 않아야 한다.
7. 사용자로서, `%20`이나 한글처럼 퍼센트 인코딩된 경로도 원래 파일 이름으로 찾아지길 원한다.
8. 사용자로서, 정적 파일 주소 뒤에 쿼리스트링(`?v=2`)을 붙여도 같은 파일을 받고 싶다. 그래야 캐시 무효화용 쿼리를 쓸 수 있다.
9. 사용자로서, `HEAD`로 요청하면 본문 없이 GET과 같은 헤더를 받고 싶다. 그래야 `curl -I`로 확인할 수 있다.
10. 사용자로서, `POST /api/echo`에 보낸 본문을 바이트 그대로(이진 데이터, UTF-8 포함)돌려받고 싶다. 그래야 POST 본문 처리를 확인할 수 있다.
11. 사용자로서, `GET /api/whoami`로 응답한 서버의 이름과 포트를 받고 싶다. 그래야 어느 백엔드가 응답했는지 안다.
12. 사용자로서, 정적 파일에 POST하면 405와 `Allow` 헤더를 받고 싶다. 그래야 어떤 메서드가 되는지 안다.
13. 사용자로서, 모든 응답에 `Content-Type`(본문이 있을 때), `Content-Length`, `Connection`, `Date`, `Server`가 붙길 원한다. 그래야 클라이언트가 응답 끝을 정확히 안다.
14. HTTP/1.1 클라이언트로서, 따로 말하지 않아도 연결이 유지되길 원한다. 그래야 페이지 하나에 딸린 파일을 연결 하나로 받는다.
15. 클라이언트로서, `Connection: close`를 보내면 응답 뒤에 연결이 닫히길 원한다.
16. HTTP/1.0 클라이언트로서, 기본은 응답 뒤에 닫히고 `Connection: keep-alive`를 보낼 때만 유지되길 원한다.
17. 클라이언트로서, 요청 두 개를 한 번에 이어 보내도(파이프라이닝) 순서대로 두 응답을 받고 싶다. 그래야 TCP가 요청을 어떻게 쪼개거나 붙여 보내도 상관없다.
18. 클라이언트로서, 요청이 여러 번에 나뉘어 도착해도 하나의 요청으로 처리되길 원한다.
19. curl 사용자로서, 큰 본문을 POST할 때 `Expect: 100-continue`에 `100 Continue`를 바로 받고 싶다. 그래야 1초씩 기다리지 않는다.
20. 클라이언트로서, 지원하지 않는 `Expect` 값을 보내면 417을 받고 싶다.
21. 클라이언트로서, 본문이 한도(1 MiB)보다 크면 본문을 다 보내기 전에 413을 받고 싶다.
22. 클라이언트로서, 요청 줄이 한도보다 길면 414, 헤더가 한도보다 크거나 많으면 431을 받고 싶다.
23. 클라이언트로서, 요청 줄이나 헤더 형식이 깨졌으면 400을 받고 연결이 닫히길 원한다.
24. 클라이언트로서, 모르는 메서드는 501, 지원하지 않는 HTTP 버전은 505를 받고 싶다.
25. HTTP/1.1 클라이언트로서, `Host` 헤더 없이 보내거나 두 번 보내면 400을 받고 싶다.
26. 클라이언트로서, POST에 `Content-Length`가 없으면 411, `Transfer-Encoding`을 쓰면 501을 받고 싶다.
27. 클라이언트로서, `Content-Length`가 숫자가 아니거나, 음수거나, 넘치거나, 서로 다르게 두 번 오면 400을 받고 싶다.
28. 다른 사용자로서, 요청을 한 바이트씩 아주 느리게 보내는 클라이언트가 작업자를 오래 붙잡지 않길 원한다. 요청 deadline이 지나면 그 연결은 408을 받고 닫힌다.
29. 사용자로서, 루트 밖을 가리키는 경로(`..`, 인코딩된 `%2e%2e`, 심볼릭 링크)로는 어떤 파일도 받을 수 없길 원한다.

### 서버를 띄우는 사람(운영자)

30. 운영자로서, 포트·호스트·정적 파일 루트를 CLI 인자로 정하고 싶다.
31. 운영자로서, 작업자 수와 연결 큐 크기를 CLI 인자로 정하고 싶다. 그래야 부하 측정 때 바꿔 볼 수 있다.
32. 운영자로서, `--route`로 경로 접두사와 백엔드 목록을 여러 개 지정하고 싶다.
33. 운영자로서, `--name`으로 서버 이름을 붙이고 싶다. 그래야 같은 실행 파일로 띄운 백엔드 A, B를 구분한다.
34. 운영자로서, 인자가 틀리거나, 루트가 없거나, 라우트 형식이 틀리면 사용법과 함께 종료 코드 2로 바로 끝나길 원한다.
35. 운영자로서, 포트가 이미 쓰이는 등 `bind`가 실패하면 이유를 보고 종료 코드 1로 끝나길 원한다.
36. 운영자로서, 서버를 껐다 바로 켜도 같은 포트에 `bind`되길 원한다(`SO_REUSEADDR`).
37. 운영자로서, Ctrl-C(SIGINT)나 SIGTERM을 보내면 새 연결 받기를 멈추고, 처리 중인 요청은 마치고, 자원을 정리한 뒤 종료 코드 0으로 끝나길 원한다.
38. 운영자로서, 요청마다 접근 로그 한 줄(시각, 클라이언트 주소, 메서드, 경로, 상태 코드, 보낸 바이트, 걸린 시간)을 보고 싶다.
39. 운영자로서, 연결 큐가 가득 차면 새 연결이 503을 바로 받길 원한다. 그래야 서버가 멈춘 것처럼 보이지 않는다.
40. 운영자로서, 응답을 보내는 도중 클라이언트가 끊어도 서버가 죽지 않고(SIGPIPE 무시) 그 연결의 메모리와 FD가 회수되길 원한다.
41. 운영자로서, keep-alive 연결이 할 일 없이 작업자를 붙잡지 않길 원한다. 유휴 시간이 지나거나 연결당 요청 수 한도에 닿으면 연결을 닫는다.

### Reverse Proxy

42. 사용자로서, 경로 접두사(`/api/`)가 라우트에 걸리면 요청이 백엔드로 전달되고 응답을 그대로 받고 싶다. 경로와 쿼리는 바뀌지 않는다.
43. 운영자로서, 라우트가 여러 개면 가장 긴 접두사가 이기길 원한다(`/api/admin/`이 `/api/`보다 먼저).
44. 운영자로서, `/service` 라우트가 `/service`와 `/service/x`에는 걸리고 `/service-other`에는 걸리지 않길 원한다.
45. 운영자로서, 한 라우트의 백엔드들이 A → B → A 순서(라운드 로빈)로 요청을 나눠 받길 원한다.
46. 사용자로서, 라우트에 걸리지 않는 경로는 프록시가 직접 정적 파일이나 동적 엔드포인트로 응답하길 원한다.
47. 사용자로서, 백엔드가 연결을 거부하거나 깨진 응답을 보내면 502를 받고 싶다.
48. 사용자로서, 백엔드가 응답하지 않으면 정해진 시간(3초) 뒤 504를 받고 싶다. 작업자도 그때 풀려나야 한다.
49. HTTP/1.0 클라이언트로서, 백엔드가 chunked로 응답해도 `Content-Length`가 붙은 응답을 받고 싶다.
50. 백엔드 개발자로서, `X-Forwarded-For`로 실제 클라이언트 주소를 알고 싶다. 클라이언트가 보낸 값은 믿을 수 없으니 프록시가 실제 연결 주소로 덮어쓴다.
51. 백엔드 개발자로서, 클라이언트가 보낸 `Host`는 그대로 받고, `Connection` 같은 hop-by-hop 헤더는 받지 않길 원한다.
52. 사용자로서, 백엔드 연결과 상관없이 내 연결(keep-alive)은 계속 유지되길 원한다.
53. 사용자로서, 실패한 요청이 몰래 다시 보내지지 않길 원한다. 그래야 POST가 두 번 실행되지 않는다.
54. 백엔드 개발자로서, `Set-Cookie`처럼 여러 번 오는 응답 헤더가 합쳐지지 않고 따로 전달되길 원한다.

### 팀원·리뷰어

55. 팀원으로서, HTTP 파서, MIME 매핑, 경로 검사, 라우트 매칭·라운드 로빈, 백엔드 응답 해석을 소켓 없이 단위 테스트하고 싶다.
56. 팀원으로서, `make test` 한 번으로 단위 테스트와 실제 소켓 통합 테스트를 다 돌리고 싶다.
57. 팀원으로서, ASan·UBSan 빌드와 Linux의 valgrind로 누수와 잘못된 메모리 접근이 없다는 걸 확인하고 싶다.
58. 팀원으로서, `ab`로 정적·프록시 × 동시 접속 수 × keep-alive 켜고 끔의 처리량을 재고 기록으로 남기고 싶다.
59. 팀원으로서, WSL2 Ubuntu와 macOS에서 같은 소스가 고치지 않고 빌드되길 원한다.
60. 리뷰어로서, PR마다 CI가 포맷 검사, 경고를 오류로 보는 빌드, 테스트, sanitizer 테스트를 돌리길 원한다.
61. 리뷰어로서, 데모 페이지(HTML·CSS·JS·이미지)에서 정적 응답, POST, 백엔드 A/B 번갈아 응답을 브라우저로 바로 확인하고 싶다.

### Forward Proxy

번호는 앞의 이야기를 이슈에서 번호로 가리키고 있어서 이어 붙였다.

62. 운영자로서, `--forward-allow 127.0.0.1/32`처럼 허용 목록을 줄 때만 포워드 프록시가 켜지길 원한다. 그래야 켜 놓고 막는 걸 잊어 열린 프록시가 되는 일이 없다.
63. 운영자로서, 허용 목록 밖 클라이언트의 포워드 요청은 403을 받길 원한다.
64. 운영자로서, 허용 목록 형식이 틀리거나 16개를 넘으면 사용법과 함께 종료 코드 2로 끝나길 원한다.
65. 운영자로서, 포워드 프록시를 켜지 않으면 absolute-form 요청은 지금처럼 400, CONNECT는 501을 받길 원한다.
66. 운영자로서, 포워드 프록시와 라우트를 같이 켜도 포워드 요청은 라우트를 타지 않고, origin-form 요청은 지금 순서대로 처리되길 원한다.
67. curl 사용자로서, `curl -x http://127.0.0.1:8080 http://목적지/경로`로 목적지 서버의 응답을 그대로 받고 싶다. GET·HEAD·POST가 다 된다.
68. 목적지 서버 개발자로서, 프록시를 거친 요청도 origin-form 요청 줄과 URI의 host:port가 담긴 `Host`로 받고 싶다. 클라이언트가 보낸 `Host`는 무시된다.
69. 목적지 서버 개발자로서, `Proxy-Connection`, `Proxy-Authorization` 같은 프록시용 헤더는 받지 않길 원한다.
70. 사용자로서, 포트를 안 쓴 URI는 80, 경로가 빈 URI는 `/`로 가길 원한다.
71. 사용자로서, `https://` absolute-form, userinfo(`user@host`), IPv6 리터럴은 400을 받고 싶다.
72. 사용자로서, 목적지 이름을 찾지 못하거나 연결이 거부되면 502, 목적지가 응답하지 않으면 3초 뒤 504를 받고 싶다. 내 keep-alive 연결은 그 뒤에도 유지된다.
73. 브라우저·curl 사용자로서, `CONNECT host:port`로 터널을 열어 HTTPS 사이트를 프록시 너머로 쓰고 싶다. 프록시는 TLS 안을 보지 않는다.
74. 클라이언트로서, CONNECT 머리 바로 뒤에 이어 보낸 바이트(예: TLS ClientHello)가 버려지지 않고 목적지 서버로 가길 원한다.
75. 운영자로서, 양쪽 모두 5초 동안 바이트가 없는 터널은 닫혀서 작업자가 풀려나길 원한다.
76. 운영자로서, SIGINT·SIGTERM을 보내면 열린 터널도 바로 닫히고 서버가 종료 코드 0으로 끝나길 원한다.
77. 클라이언트로서, CONNECT 대상이 `host:port` 형식이 아니면 400, 연결 실패는 502, 시간 초과는 504를 받고 연결이 닫히길 원한다.
78. 팀원으로서, absolute-form·authority-form 파싱과 허용 목록 검사를 소켓 없이 단위 테스트하고 싶다.
79. 리뷰어로서, README의 `curl -x` 예시(http, https)를 그대로 따라 해서 포워드 프록시를 확인하고 싶다.

### 계약

첫 티켓은 계약이다. 모듈끼리 쓰는 타입(설정, 라우트, 백엔드, 요청, 헤더), 한도 상수, 함수 선언을 공통 헤더 하나에 정하고, 같은 티켓에서 CI를 만든다. 순수 함수 인터페이스는 이렇게 생긴다.

- **요청 파싱**: 버퍼와 길이를 받아 셋 중 하나를 돌려준다. 완성(머리 길이), 더 받아야 함, 오류(보낼 HTTP 상태 코드). 요청에는 메서드, 대상 원문, 경로, 쿼리, 버전(1.0/1.1), 헤더 목록, `Content-Length`, keep-alive 여부가 담긴다. 포워드 프록시를 넣으면서 요청 대상의 형식(origin·absolute·authority)과 목적지 host·포트가 더해졌다. absolute-form의 경로와 쿼리는 URI 안의 경로 부분이다.
- **MIME 매핑**: 경로 → `Content-Type`. 확장자는 대소문자를 가리지 않고, 모르면 `application/octet-stream`.
- **경로 검사**: 요청 경로 → 디코딩된 안전한 상대 경로, 또는 오류(400/403).
- **라우트**: (라우트 목록, 경로) → 걸린 라우트 또는 없음. (라우트) → 다음 백엔드.
- **백엔드 응답 해석**: 받은 바이트 전부 → 상태 코드, 헤더 목록, 본문(chunked는 풀어서), 또는 오류.
- **허용 목록 검사**: (허용 목록, 클라이언트 IPv4 주소) → 허용 여부.

|---|---|---|
| `--host` | `127.0.0.1` | IPv4 주소 |
| `--port` | `8080` | 1~65535 |
| `--root` | `public` | 있는 디렉터리 |
| `--workers` | `8` | 1~128 |

종료 코드: 0 정상 종료, 1 실행 중 오류(`bind` 실패 등), 2 인자 오류.

### HTTP 범위와 한도

| 항목 | 규칙 |
|---|---|
| 메서드 | GET, HEAD, POST. 포워드 프록시가 켜져 있으면 CONNECT도. 그 밖의 메서드는 501 |
| 버전 | `HTTP/1.0`, `HTTP/1.1`. 형식은 맞는데 다른 버전이면 505, 형식이 틀리면 400 |
| 요청 대상 | origin-form(`/`로 시작). 포워드 프록시가 켜져 있으면 GET·HEAD·POST의 absolute-form(`http://`)과 CONNECT의 authority-form(`host:port`)도. 아니면 400 |
| 줄 끝 | CRLF. LF 하나만 와도 줄 끝으로 받는다 |
| 요청 줄 | 8 KiB까지. 넘으면 414 |
| 헤더 | 머리 전체 16 KiB, 64개까지. 넘으면 431. 이름에 공백이 있거나 줄이 이어지면(obs-fold) 400 |
| 본문 | `Content-Length` 바이트만큼 읽는다. 1 MiB까지, 넘으면 본문을 읽기 전에 413 |
| `Content-Length` | 숫자만. 넘침이나 서로 다른 중복은 400. POST에 없으면 411 |
| `Transfer-Encoding` | 요청에 있으면 501(chunked 요청 본문은 받지 않는다) |
| `Host` | HTTP/1.1에서 필수. 없거나 중복이면 400 |
| `Expect` | `100-continue`면 본문 전에 `100 Continue`. 다른 값은 417 |
| 오류 뒤 연결 | 파싱 오류(400), 408, 411, 413, 414, 417, 431, 501, 505 응답 뒤에는 연결을 닫는다. 본문 경계를 믿을 수 없어서다 |

### 응답

- 상태 줄은 `HTTP/1.1 <코드> <문구>`.
- 항상 `Date`, `Server`, `Content-Length`, `Connection: keep-alive|close`를 붙인다. 본문이 있으면 `Content-Type`도. 텍스트 계열은 `; charset=utf-8`.
- 오류 응답 본문은 상태 코드와 문구를 담은 짧은 HTML.
- 405에는 `Allow`를 붙인다.

### keep-alive와 시간 한도

| 항목 | 값 | 넘으면 |
|---|---|---|
| 요청 deadline | 첫 바이트부터 본문 끝까지 5초. 한 바이트씩 와도 늘어나지 않는다 | 408 보내고 닫기 |
| keep-alive 유휴 | 다음 요청의 첫 바이트를 5초 기다린다 | 조용히 닫기 |
| 연결당 요청 수 | 100 | 100번째 응답에 `Connection: close` |
| 백엔드 deadline | 연결 + 송신 + 수신 전체 3초. 목적지 서버도 같다(DNS 시간은 빼고) | 504 |
| 터널 유휴 | 양쪽 모두 5초 동안 바이트가 없으면 | 양쪽을 닫기 |

- 읽기 버퍼에 다음 요청 바이트가 남아 있으면 버리지 않고 이어서 처리한다(파이프라이닝).
- 연결 하나를 작업자 하나가 맡는 구조라 keep-alive 연결은 작업자를 붙잡는다. 위 한도로 상한을 둘 뿐 C10K를 목표로 하지 않는다. README에 이 트레이드오프와 다음 단계(이벤트 루프)를 적는다.

### 동시성

- 메인 스레드는 `accept`만 하고 연결 FD를 큐에 넣는다. 큐가 가득 차면 메인 스레드가 503을 한 번 보내 보고 바로 닫는다.
- 작업자는 큐에서 FD를 꺼내 그 연결이 끝날 때까지 맡는다. 터널도 끝날 때까지 작업자 하나를 쓴다. 동시 터널 수는 제한하지 않고, 브라우저로 쓸 때는 `--workers`를 늘리라고 README에 적는다.
- mutex는 큐만 지킨다. 네트워크 I/O 중에는 어떤 잠금도 잡지 않는다.
- 작업자 스레드는 SIGINT·SIGTERM을 막아 두고 메인 스레드만 받는다.

### 정적 파일

- 루트는 시작할 때 절대 경로로 바꾸고 디렉터리인지 확인한다.
- 쿼리를 떼고 `%XX`를 디코딩한다. 잘못된 인코딩은 400. NUL, 제어 문자, `.`·`..` 경로 요소는 403.
- 루트에서부터 경로 요소를 하나씩 `openat` + `O_NOFOLLOW`로 연다. 심볼릭 링크는 따라가지 않고 403.
- 디렉터리면 `index.html`, 없으면 403. 일반 파일이 아니면 403.
- 열기 실패는 `ENOENT`·`ENOTDIR` → 404, `EACCES` → 403, 그 밖 → 500.
- 파일은 고정 크기 버퍼로 나눠 보낸다. 파일 전체를 메모리에 올리지 않는다.
- MIME: `html`·`htm`, `css`, `js`·`mjs`, `json`, `png`, `jpg`·`jpeg`, `gif`, `svg`, `ico`, `webp`, `txt`, `pdf`, `wasm`. 나머지는 `application/octet-stream`.

### 동적 엔드포인트

라우트에 걸리지 않았을 때만 처리한다. 그래서 프록시에서는 `/api/`가 백엔드로 가고, 백엔드(라우트 없음)에서는 같은 경로를 C 로직이 처리한다.

| 경로 | 메서드 | 응답 |
|---|---|---|
| `/api/whoami` | GET, HEAD | 200 `application/json`. 서버 이름과 포트 |
| `/api/echo` | POST | 200. 본문을 그대로. `Content-Type`은 요청 값, 없으면 `application/octet-stream` |

두 경로에 다른 메서드가 오면 405 + `Allow`. `/api/` 아래 다른 경로는 정적 파일 찾기로 넘어간다(보통 404).

### Reverse Proxy

- **매칭**: 쿼리를 뗀 원문 경로(디코딩하지 않음)로 비교한다. 가장 긴 접두사가 이긴다. 접두사가 `/`로 끝나면 그대로 비교하고, 아니면 접두사 다음 글자가 없거나 `/`일 때만 걸린다.
- **선택**: 라우트마다 카운터 하나로 라운드 로빈. 카운터만 잠깐 잠그고 I/O 중에는 잠그지 않는다.
- **요청 재작성**: 메서드와 대상은 원문 그대로, 버전은 `HTTP/1.1`. 클라이언트 헤더를 복사하되 hop-by-hop 헤더(`Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`, `Connection`에 적힌 이름), `Expect`, `X-Forwarded-For`는 빼고 `Connection: close`, `X-Forwarded-For: <실제 연결 주소>`, 새 `Content-Length`를 붙인다. `Host`는 그대로 둔다.
- **응답**: 백엔드 연결은 요청마다 새로 열고 `Connection: close`로 쓴다. 백엔드가 닫을 때까지 8 MiB까지 받아 해석한다. 본문 길이는 `Content-Length`, chunked(풀어서), 연결 종료 순으로 정한다. hop-by-hop 헤더를 빼고 `Content-Length`와 `Connection`을 새로 써서 클라이언트에 보낸다. HEAD 요청과 204·304 응답에는 본문이 없다. 중복 헤더는 각각 따로 보낸다.
- **실패**: 연결 실패, 깨진 응답, 8 MiB 초과는 502. deadline 초과는 504. 다른 백엔드로 다시 보내지 않는다.

### Forward Proxy

결정과 이유는 [ADR-0001](adr/0001-forward-proxy.md)에 있다.

- **켜기와 접근 제한**: `--forward-allow`가 하나라도 있어야 켜진다. 포워드 요청을 보낸 클라이언트의 연결 주소가 허용 목록에 없으면 403. 목적지 서버와 포트는 제한하지 않는다. `Proxy-Authorization` 인증은 하지 않는다.
- **분기**: 요청 대상의 형식으로 가른다. absolute-form과 CONNECT는 포워드 프록시로, origin-form은 라우트 → 동적 엔드포인트 → 정적 파일로 간다. 포워드 요청에는 라우트를 적용하지 않는다. 꺼져 있으면 absolute-form은 400, CONNECT는 501로 지금과 같다.
- **absolute-form**: scheme은 `http`만(대소문자 무시). 포트가 없으면 80, 경로가 비었으면 `/`. `https://`, userinfo, IPv6 리터럴, 빈 host는 400(파싱 오류라 연결을 닫는다). 클라이언트가 보낸 `Host`는 무시하고 URI의 host:port를 쓴다. HTTP/1.1에서 `Host` 헤더가 있어야 하는 규칙은 그대로다.
- **목적지 주소**: 요청마다 `getaddrinfo`(IPv4만)로 찾아 첫 주소로 연결한다. 이름을 찾지 못하면 502. DNS 시간은 백엔드 deadline에 들어가지 않는다.
- **요청 재작성**: 리버스 프록시의 재작성과 같고 셋이 다르다. 요청 줄은 origin-form(`메서드 경로?쿼리 HTTP/1.1`), `Host`는 URI의 host:port, `Proxy-Authorization`은 뺀다. `X-Forwarded-For`도 실제 연결 주소로 덮어쓴다.
- **응답과 실패**: 리버스 프록시와 같다(8 MiB, 3초, 502·504, 재시도 없음, chunked 풀기, 중복 헤더 따로). 403·502·504 뒤에도 클라이언트의 keep-alive는 유지된다. 목적지 서버가 자기 자신이어도 origin-form으로 보내니 고리가 생기지 않는다.
- **CONNECT**: 대상은 `host:port`(포트 필수)만. 다른 형식이면 400, GET·HEAD·POST가 authority-form이면 400. 목적지 서버에 연결되면 `HTTP/1.1 200 Connection Established`를 `Content-Length` 없이 보낸다. 머리 뒤에 이미 받은 바이트는 목적지 서버로 먼저 넘긴다.
- **터널**: 두 소켓을 함께 `poll`하며 읽은 만큼 반대쪽에 쓴다. 양쪽 모두 5초 동안 바이트가 없으면, 한쪽이 EOF를 보내거나 오류가 나면, 서버가 종료 중이면 양쪽을 닫는다. 반쪽 닫기는 하지 않는다. 전체 시간 상한은 없다.
- **CONNECT 뒤 연결**: 성공이든 실패(403·502·504)든 응답과 터널이 끝나면 클라이언트 연결을 닫는다.

### 시그널과 종료

- `SIGPIPE`는 무시하고 쓰기 실패는 반환값으로 처리한다.
- SIGINT·SIGTERM 핸들러는 플래그를 세우고 self-pipe에 한 바이트 쓰기만 한다.
- `accept` 루프는 리스너와 self-pipe를 함께 `poll`한다.
- 종료 순서: 리스너 닫기 → 큐에서 아직 꺼내지 않은 연결 닫기 → 처리 중인 요청은 각자 deadline 안에 마치기, keep-alive 유휴 대기 중인 연결은 바로 닫기 → 작업자 join → 메모리 해제 → 종료 코드 0.

### 메모리와 자원

- 연결마다 읽기 버퍼 하나. 머리 16 KiB로 시작하고 본문이 필요하면 한도 안에서 키운다. 연결이 끝나면 해제한다.
- 프록시 버퍼는 요청 하나가 끝나면 해제한다.
- 정상 경로든 오류 경로든 FD와 메모리를 모두 회수한다. `malloc`과 `free`는 같은 모듈 안에서 짝을 맞춘다.

### 빌드와 이식성

- C11, `_POSIX_C_SOURCE 200809L`. `-Wall -Wextra -Werror -pedantic`이 타입 검사 역할을 한다.
- 포맷은 clang-format 설정 하나로 맞추고 `make format-check`로 검사한다.
- `make` 타깃: 기본(빌드), `test`, `sanitize-test`, `valgrind`(Linux), `bench`, `format-check`, `clean`.
- WSL2 Ubuntu가 기준이고 macOS에서도 빌드·테스트가 돌아야 한다. `epoll`, `kqueue`, `sendfile`, `MSG_NOSIGNAL`처럼 한쪽 OS에만 있는 API는 쓰지 않는다.
- 서버는 표준 C 라이브러리와 POSIX API만 쓴다. 테스트와 측정에는 Python 3 표준 라이브러리, `curl`, `ab`(apache2-utils), valgrind를 쓴다.

## 테스트 결정

### 좋은 테스트

겉으로 보이는 동작만 본다. 입력 바이트를 넣고 반환값, 상태 코드, 응답 바이트를 확인한다. 구조체 안쪽이나 함수 호출 순서는 확인하지 않는다. 그래야 내부를 고쳐도 테스트가 깨지지 않는다.

### 시험 경계

경계는 두 개만 둔다.

1. **프로세스 경계(가장 높은 경계)**: 빌드한 실행 파일을 임시 포트로 띄우고 실제 TCP로 말을 건다. 동작 대부분을 여기서 확인한다.
2. **순수 함수 경계**: 요청 파싱, MIME 매핑, 경로 검사, 라우트 매칭·라운드 로빈, 백엔드 응답 해석, 허용 목록 검사. 소켓 없이 바이트만 넣는다. 과제가 모듈별 단위 테스트를 요구해서 둔다.

### 무엇을 테스트하나

- **단위 테스트(C, 프레임워크 없이 실행 파일 하나)**: 정상 요청, 나뉘어 온 머리(더 받아야 함), 각 오류 코드(400·411·414·431·501·505), `Content-Length` 경계값, 대소문자 다른 헤더 이름, MIME 표와 기본값, 경로 디코딩과 탈출 시도, 접두사 경계와 최장 일치, 라운드 로빈 순서, 백엔드 응답의 Content-Length·chunked·연결 종료 본문과 깨진 응답, absolute-form(scheme 대소문자, 포트 기본값, 빈 경로, `https`·userinfo·IPv6 400)과 authority-form(포트 없음 400, CONNECT가 아닌 메서드 400), 허용 목록의 경계 주소와 `/0`·`/32`.
- **통합 테스트(Python 3 표준 라이브러리)**: 서버와 백엔드 A/B를 띄우고 raw 소켓으로 확인한다.
  - 정적: MIME, 404·403, 디렉터리 index, 디렉터리 탈출, 심볼릭 링크, HEAD
  - 동적: 이진 POST echo, 100 Continue, 405, 411, 413
  - 연결: keep-alive 연속 요청, HTTP/1.0, 파이프라이닝, 한 바이트씩 나눠 보내기, 요청 deadline(408), 유휴 종료, 응답 중 클라이언트 강제 종료 뒤에도 서버가 계속 응답
  - 프록시: A/B 번갈아 응답, 최장 접두사, 경로·쿼리 유지, `X-Forwarded-For` 덮어쓰기, chunked 백엔드, 깨진 응답(502), 연결 거부(502), 침묵하는 백엔드(504)
  - 포워드: absolute-form GET·HEAD·POST 전달(목적지 서버가 받은 요청 줄이 origin-form, `Host`가 URI 값, `Proxy-*`가 빠짐), 허용 목록 밖 403(`--forward-allow 10.0.0.0/8`로 띄우고 127.0.0.1에서 보냄), 꺼져 있을 때 400·501, 연결 거부 502, 침묵하는 목적지 504, `.invalid` 이름 502, 라우트와 같이 켰을 때 분기
  - 터널: 에코 목적지와 바이트 주고받기, 머리 뒤에 붙은 바이트 전달, 5초 유휴에 닫힘, SIGINT에 닫히고 종료 코드 0, CONNECT 실패 뒤 연결 닫힘
  - 동시성: 동시 접속 여러 개가 모두 응답받기, 큐 초과(503)
  - 종료: SIGINT 뒤 종료 코드 0
  - 가짜 백엔드(침묵, 깨진 응답, chunked)는 테스트 안에서 Python으로 띄운다.
- **curl 스모크**: 데모 자산의 `Content-Type`, 프록시 A/B 번갈아 응답, UTF-8 POST, `curl -x`(포워드)와 `curl -x --proxytunnel`(TLS 없이 CONNECT 경로).
- **메모리**: ASan + UBSan 빌드로 통합 테스트를 돌린다(macOS·Linux). Linux에서는 valgrind(`--leak-check=full`, 오류가 있으면 실패)로 서버를 띄워 통합 테스트를 돌리고 SIGINT로 끈 뒤 누수와 남은 FD가 없는지 본다.
- **부하**: `ab`로 정적·프록시 × 동시 접속 1/10/50/100 × keep-alive 켜고 끔. 요청 수를 고정하고 failed와 non-2xx도 기록한다. 결과는 문서로 남긴다.

### 앞선 예

이 레포에는 아직 테스트가 없다. 참고 구현의 테스트 구성(C 단위 테스트 + Python 통합 테스트)을 동작만 보고 새로 쓴다.

### CI

GitHub Actions에서 Ubuntu는 `format-check`, 빌드, `test`, `sanitize-test`, `valgrind`를, macOS는 빌드와 `test`를 돌린다. 계약 티켓에서 만들고 dev 브랜치 규칙의 필수 검사에 더한다(관리자 kuk-hwan이 건다).

## 범위 밖

- 프록시 캐시
- 포워드 프록시의 `Proxy-Authorization` 인증, HTTPS 가로채기(MITM), 상위 프록시로 넘기기, 목적지 제한(사설망 차단·포트 제한), 동시 터널 수 제한, 목적지 쪽 연결 재사용
- `https://` absolute-form, IPv6 목적지, DNS 시간 제한
- TLS/HTTPS, HTTP/2·3, WebSocket(`Upgrade`)
- chunked 요청 본문, Range, 압축, ETag·`If-Modified-Since`
- CGI, 디렉터리 목록
- 백엔드 연결 풀, 상태 확인, 자동 재시도·failover, 가중치 로드 밸런싱, 호스트 헤더 라우팅
- 8 MiB가 넘는 백엔드 응답(스트리밍 전달)
- 설정 파일, 실행 중 설정 다시 읽기, 실행 중 DNS 갱신
- 이벤트 루프(`epoll`·`kqueue`) 기반 동시성과 C10K
- IPv6 리스너

## 그 밖에

- 참고 구현([kuk-hwan/mini-webserver](https://github.com/kuk-hwan/mini-webserver))은 동작만 보고 새로 쓴다. 처음 결정은 참고 구현과 같은 방향이라 ADR이 없었다. 참고 구현에 없는 포워드 프록시는 [ADR-0001](adr/0001-forward-proxy.md)로 남겼다. 용어는 루트의 `GLOSSARY.md`를 따른다.
- 단계 제안(티켓 만들 때 마일스톤과 `stage:*` 라벨로 쓴다):
  1. `stage:1` 기본 서버: 계약 + CI, 리스너·스레드 풀·시그널, HTTP 파서, 정적 파일
  2. `stage:2` 동적·프록시: 동적 엔드포인트, keep-alive·파이프라이닝, 라우트·라운드 로빈, 백엔드 전달
  3. `stage:3` 품질: 통합 테스트 보강, sanitizer·valgrind, 부하 측정 기록, README·데모 페이지
  4. `stage:4` 포워드 프록시: 요청 대상 형식 계약, absolute-form 전달과 허용 목록, CONNECT 터널, README
- `area:*` 라벨은 모듈 이름을 그대로 쓴다(`area:http`, `area:proxy` 등).
